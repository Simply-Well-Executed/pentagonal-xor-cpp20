## CURRENT operator decision: zero GNU and zero POSIX approvals (2026-11-20)

The owner explicitly clarified that **no GNU or POSIX components are approved anywhere in the repository, project, organization or related hierarchy**, including build-only tools and disposable container stages. This **supersedes** the earlier permission for LGPL-2.1-only, which is a GNU license. The current [LOCK.tsv](../LICENSES/LOCK.tsv) marks both LGPL-2.1-only and LGPL-2.1-or-later **FORBIDDEN** without deleting their exact texts or earlier Git revisions. Preferred: 0BSD (the only approved BSD-family identifier), MIT, MPL-2.0, and CDDL-1.0; official Oracle Java remains subject to the actual vendor terms, component provenance and third-party dependencies.

**POSIX is an interface standard, not a software license.** A `$name` shell expansion is not a GNU copyright grant. GNU licenses and authored POSIX execution are two separate owner-defined denial predicates; neither permits the other by implication. No auto-executed GNU/POSIX development or build probe is approved. The old Linux/Docker pipeline was replaced in this draft PR by a PowerShell-based Windows-hosted **reference-integrity-only** gate. Other tracked `.sh` files, older Dockerfiles and branch-scoped workflows require separately inventoried replacements, not silent deletion. The existing source check is expected to fail until migration completes.

The present PR **does not establish zero GNU/POSIX across other organization repositories, inherited toolchains or previously published artifacts**. Their status remains Needs Review/HOLD. No CI success, historic build, or source presence conveys an implicit exception. See [zero-approval migration protocol](GNU_POSIX_ZERO_APPROVAL_POLICY.md).

5. All probing uses **GitHub-hosted** Ubuntu runners, exact Git commit, Docker registry digests, SHA256-verified upstream artifacts, no author-created Node/npm/Python pipeline, and no user-local or self-hosted compute. Build/test exceptions do not imply production distribution consent.
6. MagicComb **HEAD** protects source and artifact identity before input evaluation/extraction. **TAIL** revalidates post-test image/reports and prevents promotion if metadata, sources, licenses or CVEs do not satisfy policy. ## CVE-2026-97054 exact executable provenance and scoped remediation

GitHub-hosted [run #44766220131](https://github.com/Simply-Well-Executed/pentagonal-xor-cpp20/actions/runs/44766220131) verified that the inherited Linux/amd64 Go-based executable is `/usr/bin/pebble`, exactly **10,584,224 bytes** with SHA256 `5e9859b77a7ed5c4421f5c43435cc3822d5090d0f4ced422adade068e3b974e3`. `dpkg-query -S /usr/bin/pebble` returned **not owned by a Debian package**. Docker Scout independently attributed the medium finding to this file, `pkg:golang/stdlib@1.27.3`, fixed in Go 1.27.4. This is not an Oracle Java or PowerShell file.

Experimental GitHub commit [`c134f7b8ef9d`](https://github.com/Simply-Well-Executed/pentagonal-xor-cpp20/commit/c134f7b8ef9def72f93bd70c39a9b99583e89d82) proposes a narrowly scoped **removal only from the newly built, unpublished trial image**, not from history or the Microsoft original base: require existing non-symlink file, **exact SHA256 match**, and still-unowned `dpkg-query` state before removing it, with explicit `IRON|MAGICCOMB|PEBBLE|REMOVED` audit. A changed upstream binary or package owner makes the build fail. Full CTest, Java and Docker Scout validation are still required to establish that removing the unused binary is safe and actually eliminates the CVE.

**No release permitted even if this CVE reaches zero:** the GNU/EPL policy remains blocked pending source-matched licensing of distributable files, and Oracle NFTC review remains separate. Any CVE reduction is evidence, not permission.
## Zero-reported-CVE experimental result, and why release remains blocked

GitHub-hosted [MagicComb HEAD/TAIL run #44767653120](https://github.com/Simply-Well-Executed/pentagonal-xor-cpp20/actions/runs/44767653120) validated the unpublished source commit [`a5e3c9668c4b797bb0120d1132a8ded5514996b6`](https://github.com/Simply-Well-Executed/pentagonal-xor-cpp20/commit/a5e3c9668c4b797bb0120d1132a8ded5514996b6). After verifying and removing the precise unowned vulnerable `/usr/bin/pebble`, the Dockerfile assembled a **fresh root-filesystem layer using a scratch final stage**. This preserved the original Microsoft base registry digest and the HEAD/TAIL logs but prevented an obsolete, removed binary in an inherited layer from being included in the exported experimental image.

The independent Docker Scout v1.29.0 report on the new **local-only** experimental image (`swe-magiccomb-oracle27-dotnet11-ps77:a5e3c9668c4b797bb0120d1132a8ded5514996b6`) found **0 critical, 0 high, 0 medium, 0 low** vulnerabilities across **1,003 indexed components**. A separate targeted scan for `CVE-2026-97054` returned **no vulnerable package detected**. The image passed **45/45 C++20 CTests**, **26,654 Java checks**, Oracle Java 27 / PowerShell 7.7 / .NET 11 version checks, and the no-Python runtime guard. Scout confirms non-root default execution.

**A zero-reported-CVE scanner result does NOT mean an image is free from unreported, undiscovered or context-specific risk.** Supply-chain evaluation still failed **5/7 policy criteria**: Docker Scout counted **563 copyleft-licensed package records** and **two missing supply-chain attestations**. The independent conservative GNU/EPL metadata gate found **161 records requiring review**, with **0 missing-copyright-path records** after multiarchitecture normalization. These counts represent different scopes and methods, not interchangeable GPL-only proof. Oracle NFTC and its third-party notices remain a separate explicit licensing review.

The cloud workflow **correctly returned FAILURE/HOLD, with no GHCR/Docker Hub push or production deployment**. `EXC-GNU-LINUX-001` [issue #29](https://github.com/Simply-Well-Executed/pentagonal-xor-cpp20/issues/29) is still awaiting an explicit answer about disposable build-only GNU components. CVE [issue #30](https://github.com/Simply-Well-Executed/pentagonal-xor-cpp20/issues/30) must retain the original finding and the experimental mitigation evidence; closing it as a production remediation would be premature. The older published Docker Hub candidate continues to report **3C/89H/204M/162L** and remains unchanged.
