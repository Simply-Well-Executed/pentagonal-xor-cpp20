This is an *additional*, explicitly labeled **bytewise XOR buffer transformation** library. The established `pentagonal_xor` executable implements a five-input odd-parity probability score; that algorithm and its existing public headers remain authoritative and unchanged by this new module. ## Frozen semantics: two distinct byte streams

**1. Exact-seeded formula where its integer arithmetic is representable:** At offset `i`, `apply_pentagonal_xor(buffer, seed)` uses `P_(seed+i) = (seed+i)(3(seed+i)-1)/2`, then derives a byte as `(p ^ (p >> 8) ^ (p >> 16)) & 255`. The function's `uint64_t` arithmetic has finite range and wraps on overflow; beyond the representable domain it must **not** be described as arbitrary-precision, exact pentagonal arithmetic.

**2. Periodic LUT formula:** `PENTAGONAL_LUT[0..255]` is generated by a C++20 `consteval` lambda from `P_1..P_256`. `fast_xor_buffer` repeats those 256 bytes with `i & 255`. **After offset 255 this does not generally equal the exact-seeded stream**. Both transforms are XOR involutions when called twice using the same algorithm/seed. Neither should be silently substituted for the other in saved streams, ledger identities or interoperability protocols.

For each full 8-byte span, the fast API copies a payload word and key word with `std::memcpy`, XORs `std::uint64_t` values, then copies the result back. The remaining 0..7 bytes use the same LUT indexing. The two `memcpy` operands have identical byte order on the same machine, so the XOR bytes do not depend on endianness. Copies are well-defined for unaligned payloads. **A source-level 8-byte loop does not guarantee one MOV instruction or a particular speedup**: measure optimized machine code on each compiler and CPU.

`ObfuscatedData` compiles known literals into an XOR-obfuscated array, with the seed and decryption recipe still present in the binary. This is **not** encryption, protected key storage or a defense against reverse engineering.

`fixed_mul` defines signed product division that truncates toward zero (not every historical fixed-point implementation's negative rounding). Inputs resulting outside `int32_t` representability are outside its contract.

## CPU scheduling, caches and NUMA

- At startup, the benchmark requests **moderate**, not time-critical, priority and a best-effort affinity to its current logical core *before* allocating or touching the payload buffer.
- Windows uses the group-aware `GetCurrentProcessorNumberEx` / `SetThreadGroupAffinity` interface. Linux uses `sched_getcpu` / `sched_setaffinity` with CPU set bounds checked. Other platforms report unsupported.
- The operating system can decline a request. The CLI prints the real outcome; `--strict-affinity` returns an error instead of running when a required pin is rejected. There is no privilege escalation, persistent thread-policy modification, or fake success report.
- Affinity does **not guarantee** L1 residency, exclusive cache use, fixed CPU frequency, absence of preemption, or NUMA page locality. Strict NUMA locality needs topology discovery and measured policies beyond this API. A 256-byte table may fit in a cache line collection but is not locked into L1.

## Build and verify locally

ISO C++20 is required: `CXX_STANDARD 20`, `CXX_STANDARD_REQUIRED ON`, `CXX_EXTENSIONS OFF`. Release optimization is MSVC `/O2` or GCC/Clang `-O3`; other configurations retain the historical O2 policy, without introducing O0. C++ warning switches are global (`/W4 /permissive-` or `-Wall -Wextra -Wpedantic`). CMake's existing project identity and original target names are preserved.

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DCMAKE_CXX_STANDARD=20 -DCMAKE_CXX_STANDARD_REQUIRED=ON -DCMAKE_CXX_EXTENSIONS=OFF -DFETCHCONTENT_FULLY_DISCONNECTED=ON
cmake --build build --config Release --parallel
ctest --test-dir build -C Release --output-on-failure
./build/pentagonal_xor_cli --bytes 16777216
```

On Visual Studio multi-configuration builds, the CLI may be under `build/Release/pentagonal_xor_cli.exe`. The `pentagonal_xor_cli` test uses `--bytes 65536` to avoid allocating 16 MiB during every test; the default standalone demonstration allocates 16 MiB, and the explicit limit is 256 MiB. The benchmark timer measures **only one XOR pass**, excluding the allocation, checksum calculation and printing. The printed witness is deterministic, not a cryptographic integrity guarantee. Before comparing throughput, control affinity, priority, thermal state, power mode, input size, repetitions and counter methodology; no speedup has been verified here.

The local [POSIX T-CROSS executor](../ci/t-cross-posix.sh) and [YAML Taskfile](../Taskfile.yml) capture a Git-derived +/-DIFF at execution time. Their strict whole-repository residual-surface and REST-source gates may remain blocked by historical scripts. Direct binary import checks cover both `pentagonal_xor` and `pentagonal_xor_cli`; static imports alone do not establish an isolated runtime.
